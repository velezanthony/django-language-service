# adapters

VS Code adapter layer. Every VS Code API surface the extension contributes lives here:
providers, commands, webviews, decorations and status bar. This is the **only layer
allowed to import `vscode` freely**; it may depend on `$domain`, `$infra` and `$shared`,
and nothing outside `src/adapters` imports it except `src/extension.ts`.

## Registering a new adapter

1. Export a single `register(ctx, services): vscode.Disposable` from your module.
2. Add it to the frozen `ADAPTERS` array in `index.ts` via the `a(id, register)` helper.
3. `extension.ts` iterates `ADAPTERS` and calls `register` inside a `try/catch`, so a
   throwing adapter is logged (`adapter <id> register failed`) instead of aborting
   activation. Never assume a sibling adapter registered successfully.

`services` is an `AdapterServices` object, not a bare closure:
`{ getProject, getScanner?, onProjectChange? }`. **Call `getProject()` inside handlers,
never at registration time** — otherwise you capture `EMPTY_PROJECT` forever. Subscribe
to `onProjectChange` to push fresh data to webviews; only `refresh-view-context` uses
`getScanner`.

**Registration order is load-bearing** (see the header of `index.ts`): `status-bar`
before diagnostics, `file-decoration/include` before `diagnostics/include-pretty`, and
`diagram/panel` before `commandsAdapter`. Do not alphabetize the list.

Commands go through `cmdId(suffix)` / `registerCmd()` in `_shared/command-helper`, which wraps
every handler in catch + log + a toast offering the log — one place rather than eighteen, some
of which had a try/catch and some of which did not. Four are intentionally internal and absent
from `package.json` (`codelens-toggle-include`, `toggleLiveByName`, `validateByName`,
`diagramBooted`) — they are invoked programmatically and carry arguments a palette entry could
not supply, or exist only so the integration suite can observe state (`diagramBooted` answers
whether the diagram webview posted its `ready` handshake). Adapters talk to the two browser bundles only through
the message types in `$shared/protocol` — never import from `src/webview` or `src/sidebar`.

The layer rule is a review-time convention; no lint rule enforces it. `src/architecture.test.ts`
asserts the boundaries either side of it — domain reaches neither `vscode` nor
`$adapters`/`$infra`, and nothing bundled for a browser reaches `$shared` — but nothing asserts
that `src/extension.ts` is still the only importer of this layer.
